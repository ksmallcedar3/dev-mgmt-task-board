1. 講義の3択 × このツール

Markdown 使わない

人間が読むメモ向き。書き方が揺れてプログラムが扱いにくい。タスク一覧の正本には不向き。

JSON 使う（今）

members・年度目標の正本。変化が少なくgitで管理できる。AIから近い場所に置けるのがメリット。

Database 将来

tasksの正本（移行予定）。複数人が同じURLで読み書きするために必要。Neon等のサービスを使う。

Markdown → 覚悟1 → JSON → 覚悟2 → Database 進むほど強力だが、考えることも増える

2. データ別 保存先一覧

データ 変化頻度 保存先 理由
tasks（タスク一覧） 週次以上 Database 変わり続ける + 将来、課員も書き込む
members（課員名簿） 数か月に1回 JSON 変化が少ない。AIから近い場所に置く
年度目標カテゴリ 年に1回 JSON 同上。Cursorで直編集・commitで反映
ワークスペース名 ほぼ変わらない JSON 設定値。触る頻度ほぼゼロ

ポイント：「週次で変わるかどうか」が JSON と DB の分岐点。変わらないものは JSON のまま git 管理でシンプルに保つ。

4. フェーズロードマップ

Phase 1 — 今

課長が集約

保存先: JSON + localStorage
課長がアプリで編集 → export → tasks.json更新 → commit → deploy
課員はVercel URLで閲覧のみ（会社PCからもアクセス可）

→
Phase 2 — 次

課員も閲覧・更新

保存先: Database（Neon等）
tasksをDBに移行。課員が同じURLでリアルタイムに最新状態を確認。課員も自分のタスクを更新できる。

→
Phase 3 — 将来

音声 → AI → 承認

保存先: Database
進捗会議の音声をAIが構造化。課長が承認ボタンを押すだけでDBに保存。ハーネスエンジニアリングの実践。

5. グループセッションで話すこと

30秒ピッチ（そのまま話せる）

このツールのデータは4種類あります。週次で変わる tasks だけ将来 Database に入れて、 滅多に変わらない課員名簿と年度目標は JSON のまま git 管理します。

将来は進捗会議の音声を AI が構造化して候補を出し、 課長が承認ボタンを押すだけで DB に入る仕組みを目指します。 これが講義で習ったハーネスエンジニアリングの実践です。
「変わる頻度で保存先を分ける」という考え方、みなさんのツールでも応用できそうですか？

補足：今すぐできること

Phase 1 として、エクスポート機能を実装 → tasks.json を更新 → commit → deploy → 課員に URL を共有する。 DB がなくても「読む」習慣を先に作れる。
